# STT / LLM 로컬화 평가 및 점진 교체 계획

| 항목 | 내용 |
|---|---|
| **작성일** | 2026-06-13 |
| **상태** | 결정 완료 — *현 파이프라인 유지, 단계별 교체 검증* |
| **관련** | [PRD §6.1·§7.2·§13](./PRD.md) · [로드맵 Phase 5](../development/roadmap.md) · [diarization.py](../../services/diarization.py) |

> 회의 STT/화자분리 및 텍스트 처리(요약·회의록·챗봇)를 로컬/오픈 모델로 전환할 수 있는지 평가한 기록. 후보로 **Gemma 4 12B**, **gpt-oss-120b/20b**를 검토했다.

---

## 1. 배경 & 문제의식

- 현재 STT는 **투 트랙**: `STT_ENGINE=local`(faster-whisper + pyannote 3.1) / `gemini`(Gemini API).
- **고통점:** 로컬 트랙이 무거워 GPU 필요(주범 = pyannote + large-v3 동시 상주), 투 트랙 유지 부담.
- **추가 관찰:** 과거 Gemini 2.5 Pro 테스트(15~20분, 화자 4~6인)는 전사·화자분리를 잘 해냈으나, 그 결과는 **LLM의 자체 교정(self-correction)** 영향을 받았음(당시 LLM과의 대화로 확인). 즉 *축자 전사가 아니라 LLM이 다시 쓴 텍스트*.

---

## 2. 후보 모델 사실 확인 (공식 모델 카드/문서 기준, 2026-06)

| 모델 | 종류 | 오디오/STT | 화자분리 | 타임스탬프 | 16GB 구동 | 비고 |
|---|---|---|---|---|---|---|
| **gpt-oss-120b** | 텍스트 전용 MoE LLM | ❌ | ❌ | ❌ | ❌(~60GB+) | 귀 없음 → STT 불가 |
| **gpt-oss-20b** | 텍스트 전용 MoE LLM | ❌ | ❌ | ❌ | ✅ | 귀 없음 → STT 불가, 텍스트 단계만 후보 |
| **Gemma 4 12B** | 인코더리스 멀티모달 | ✅ ASR/AST | ❌ 미문서화 | ❌ 미문서화 | ✅(Q4 ~8GB) | **30초 상한**, **모노 단일 채널**, 자체 교정 내장 |
| *(참조) Gemini 2.5 Pro* | 클라우드 멀티모달 | ✅ | ✅(장시간) | 추정값 | N/A | 현행 cloud 트랙 |

**출처:** [gpt-oss-120b](https://huggingface.co/openai/gpt-oss-120b) · [gpt-oss-20b](https://huggingface.co/openai/gpt-oss-20b) · [Gemma 4 12B-it](https://huggingface.co/google/gemma-4-12B-it) · [Gemma Audio 문서](https://ai.google.dev/gemma/docs/capabilities/audio?hl=ko)

### 핵심 결론
1. **gpt-oss(120b·20b)는 오디오 입력 자체가 없어** STT/화자분리 후보에서 제외. 텍스트 단계(요약/회의록/챗봇) 로컬화 후보로만 의미(16GB는 20b만).
2. **Gemma 4 12B의 ASR은 "생성형 ASR"** — Gemini와 동일하게 자체 교정 본질을 가짐(문서 프롬프트가 숫자 정규화까지 명시). 게다가 **30초 상한·화자분리/타임스탬프 미보장·모노 강제** → 회의록 제품 요건(장시간·화자·타임스탬프·confidence)과 정면으로 어긋남.

---

## 3. 검토한 대안과 기각 사유

### "Gemma 4를 STT에만, 화자분리는 pyannote 유지" (기각)
- Gemma는 타임스탬프를 주지 않으므로, pyannote와 병합하려면 **역전 파이프라인**(① pyannote로 턴 분리 → ② 각 턴 오디오를 ≤30초로 잘라 Gemma 전사)만 성립.
- 그러나 이 구조는 목표에 역행:
  - **pyannote(무거운 GPU 부분) 그대로** + **12B LLM을 턴 수만큼 수백 회 추론** → 부하 **증가**.
  - Whisper(1~3GB) < Gemma 4 12B(Q4 8GB) → STT 단이 오히려 **무거워짐**.
  - 단어 타임스탬프·음향 confidence **상실**, 짧은 조각이라 **자체 교정 악화**.

---

## 4. 결정 (Decision)

> **현재 파이프라인을 그대로 유지하고, 아래 단계를 독립적으로(설정 플래그 + 회귀 테스트 동반) 하나씩 검증·교체한다.**
> 원칙: *"듣는 일(STT·화자분리·타임스탬프)은 음향 특화 엔진에, 쓰는 일(교정·요약·회의록·챗봇)은 LLM에"* 분업.

## 5. 점진 교체 로드맵 (단계별, 독립 배포 가능)

| 단계 | 내용 | 기대 효과 | 선결 조건 |
|---|---|---|---|
| **S0 (현재)** | faster-whisper(large-v3/medium) + pyannote 3.1, `STT_ENGINE=local\|gemini` 유지 | — | — |
| **S1. STT 경량화** | faster-whisper `large-v3` → **`large-v3-turbo`** | 더 가볍고 빠름, 타임스탬프·축자성·단일 패스 유지 | 한국어 WER 실측 후 적용 |
| **S2. 화자분리/단일트랙 검토** | pyannote 유지 vs **관리형 STT+화자분리 API**(Deepgram/AssemblyAI) 1트랙화 | GPU 부담 제거, 병합 코드 제거, 비용 2~3배↓ | **프라이버시(온프레미스) 요건** 확인 + 한국어 WER·DER 실측 |
| **S3. 텍스트 단계 로컬화** | 요약/회의록/챗봇의 Gemini API → 로컬 오픈 LLM(**Gemma 4 12B** 또는 **gpt-oss-20b**) | API 비용 제거 + 프라이버시 | 한국어 요약 품질 실측으로 택일 |
| **S3-옵션. 전사 교정 패스** | 특화 ASR의 축자 전사 → **Gemma 4로 텍스트 교정**(오디오 아님) | 타임스탬프·confidence 보존하며 가독성↑, 자체 교정을 후처리에 통제 | S3과 연계 |
| **S4. 임베딩/벡터스토어** | OpenAI 임베딩 → Gemini/BGE-M3, ChromaDB → pgvector(별도 결정 대기) | 키 단일화·DB 통합 | 전체 재임베딩 동반 |

각 단계는 **설정으로 on/off**, 한국어 실측 통과 시에만 승격, 회귀 테스트 필수.

---

## 6. 측정해야 할 지표 (교체 판단 기준)
- **한국어 WER**(전사 정확도) — 실제 회의 샘플 2~3개(15~20분, 4~6인)
- **화자분리 DER**(분리 오류율) 및 체감 정확도
- **1시간 처리 시간** 및 GPU/메모리 사용량
- **자체 교정 정도** — 축자 대비 정규화/왜곡 빈도
- **비용**(회의당) — PRD §7.2 목표(로컬 시 ≤ $0.05) 대비
