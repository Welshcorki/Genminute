# Priority 2: AI 에이전트 UI 연동 - 판단 로그

## 작업 개요
회의록에서 추출된 Action Item을 UI에서 조회하고 관리할 수 있도록 구현

## 주요 판단 사항 및 결정

### 1. 데이터베이스 스키마 설계

#### 1.1 테이블 구조 결정
**판단**: `meeting_action_items` 테이블 스키마 설계
- **고려 사항**: 
  - DEV_LOG.md에 이미 설계가 있었음
  - `calendar_event_id` 필드 추가 여부
  - `tool_call_id` 필드 추가 여부
- **결정**: 
  - 기존 설계를 기반으로 하되, `calendar_event_id` 필드를 추가하여 Google Calendar 연동 상태를 추적할 수 있도록 함
  - `tool_call_id` 필드도 추가하여 향후 확장성 고려
  - `updated_at` 필드 추가하여 상태 변경 추적 가능하도록 함
- **이유**: 
  - Google Calendar 연동 상태를 UI에서 표시하기 위해 필요
  - 향후 다른 도구 연동 시 확장 가능

#### 1.2 인덱스 설계
**판단**: `meeting_id` 기준 인덱스 생성
- **결정**: `idx_action_items_meeting` 인덱스 추가
- **이유**: 회의별 Action Item 조회가 빈번할 것으로 예상

### 2. 백엔드 API 설계

#### 2.1 Action Item 추출 API
**판단**: 수동 추출 vs 자동 추출
- **고려 사항**:
  - `upload_service.py`에서 이미 자동 추출이 이루어지고 있음
  - 사용자가 수동으로 재추출할 수 있는 기능 필요 여부
- **결정**: 
  - 수동 추출 API (`POST /api/extract_action_items/{meeting_id}`) 추가
  - 자동 추출은 `upload_service.py`에서 계속 수행하되, 결과를 DB에 저장하도록 수정
- **이유**: 
  - 회의록이 업데이트되거나 재생성될 경우 재추출 필요
  - 사용자가 원할 때 수동으로 추출할 수 있는 유연성 제공

#### 2.2 회의록 텍스트 소스 결정
**판단**: Action Item 추출 시 어떤 텍스트를 사용할지
- **고려 사항**:
  - `meeting_minutes` 테이블의 회의록이 더 구조화되어 있음
  - `meeting_dialogues`의 전사본은 원문에 가까움
- **결정**: 
  - 우선 `meeting_minutes`의 회의록 사용
  - 없으면 `meeting_dialogues`의 전사본 사용
- **이유**: 
  - 회의록이 더 구조화되어 있어 Action Item 추출에 유리
  - 회의록이 없어도 전사본으로 대체 가능

#### 2.3 Agent Service 초기화 방식
**판단**: Agent Service를 언제 초기화할지
- **고려 사항**:
  - Agent Service 초기화 실패 시 전체 서비스에 영향
  - 선택적 기능으로 처리해야 함
- **결정**: 
  - 지연 초기화 방식 채택 (`get_agent_service()` 함수)
  - 초기화 실패 시 경고만 출력하고 503 에러 반환
- **이유**: 
  - Agent Service가 필수 기능이 아니므로 실패해도 다른 기능에 영향 없음
  - 사용자에게 명확한 에러 메시지 제공

### 3. 프론트엔드 UI/UX 설계

#### 3.1 Action Items 탭 위치
**판단**: 탭 순서 결정
- **고려 사항**: 
  - 기존 탭: 스크립트, 요약, 마인드맵, 회의록, 챗봇
  - Action Items의 중요도와 사용 빈도
- **결정**: 
  - 회의록 탭 다음, 챗봇 탭 전에 배치
- **이유**: 
  - 회의록과 관련된 기능이므로 인접 배치
  - 챗봇은 상호작용 기능이므로 마지막에 배치

#### 3.2 아이콘 선택
**판단**: Action Items 탭 아이콘
- **고려 사항**: 
  - 체크리스트, 할 일, 작업 등을 나타내는 아이콘
- **결정**: `CheckSquare` 아이콘 사용
- **이유**: 
  - Action Item의 완료 상태를 나타내는 체크박스와 일관성
  - 직관적이고 명확한 의미 전달

#### 3.3 빈 상태 UI
**판단**: Action Item이 없을 때 UI
- **고려 사항**: 
  - 사용자가 무엇을 해야 하는지 명확히 안내
  - 추출 버튼의 위치와 스타일
- **결정**: 
  - 중앙 정렬된 빈 상태 메시지
  - "Action Item 추출하기" 버튼 제공
  - `Sparkles` 아이콘 사용
- **이유**: 
  - 사용자에게 명확한 액션 유도
  - 일관된 디자인 패턴 (MinutesView와 유사)

#### 3.4 상태 표시 방식
**판단**: 완료/미완료 상태를 어떻게 표시할지
- **고려 사항**: 
  - 체크박스 vs 토글 버튼
  - 완료된 항목의 시각적 처리
- **결정**: 
  - 체크박스 아이콘 (`CheckCircle2` / `Circle`) 사용
  - 완료된 항목은 회색 배경, 취소선, 투명도 적용
  - 클릭 시 즉시 상태 업데이트
- **이유**: 
  - 직관적이고 일반적인 UI 패턴
  - 완료 상태를 명확히 구분

#### 3.5 날짜 표시 형식
**판단**: `due_date` 필드의 표시 형식
- **고려 사항**: 
  - ISO 8601 형식으로 저장됨
  - 한국어 사용자에게 친숙한 형식 필요
- **결정**: 
  - `toLocaleDateString('ko-KR')` 사용
  - 년, 월, 일, 시간, 분 표시
- **이유**: 
  - 한국어 사용자에게 친숙한 형식
  - 브라우저 기본 기능 활용

### 4. 데이터 흐름 설계

#### 4.1 자동 추출 vs 수동 추출
**판단**: 두 가지 추출 방식의 역할 분담
- **결정**: 
  - 자동 추출: 파일 업로드 시 자동으로 수행 (기존 동작 유지)
  - 수동 추출: 사용자가 원할 때 재추출 가능
- **이유**: 
  - 사용자 편의성 (자동) + 유연성 (수동) 제공

#### 4.2 상태 업데이트 방식
**판단**: 체크박스 클릭 시 즉시 업데이트 vs 배치 업데이트
- **결정**: 즉시 업데이트
- **이유**: 
  - 사용자 피드백이 빠름
  - 구현이 간단함
  - 실패 시 에러 메시지로 처리 가능

### 5. 에러 처리

#### 5.1 Agent Service 초기화 실패
**판단**: 초기화 실패 시 처리 방식
- **결정**: 
  - 경고 로그 출력
  - API 호출 시 503 에러 반환
  - 사용자에게 명확한 메시지 제공
- **이유**: 
  - 선택적 기능이므로 전체 서비스 중단 방지
  - 사용자에게 명확한 피드백 제공

#### 5.2 Action Item 추출 실패
**판단**: 추출 실패 시 처리 방식
- **결정**: 
  - 에러 메시지 표시
  - "다시 시도" 버튼 제공
- **이유**: 
  - 일시적 오류일 수 있으므로 재시도 기회 제공

### 6. 성능 고려사항

#### 6.1 인덱스 추가
**판단**: `meeting_id` 기준 인덱스 필요성
- **결정**: 인덱스 추가
- **이유**: 
  - 회의별 조회가 빈번할 것으로 예상
  - 데이터가 많아질수록 성능 향상

#### 6.2 데이터 로딩
**판단**: 컴포넌트 마운트 시 자동 로딩 vs 사용자 액션 시 로딩
- **결정**: 컴포넌트 마운트 시 자동 로딩
- **이유**: 
  - 사용자 경험 향상 (즉시 데이터 표시)
  - 탭 전환 시 빠른 피드백

### 7. 향후 확장성 고려

#### 7.1 추가 필드
**판단**: 향후 확장 가능한 필드
- **결정**: 
  - `tool_call_id`: 다른 도구 연동 시 추적
  - `calendar_event_id`: Google Calendar 연동 상태 추적
- **이유**: 
  - 향후 Notion, Slack 등 다른 도구 연동 시 확장 가능

#### 7.2 상태 값 확장
**판단**: 상태 값의 확장 가능성
- **결정**: 
  - 현재: `pending`, `done`
  - 향후: `failed`, `in_progress` 등 추가 가능
- **이유**: 
  - 유연한 상태 관리

## 구현 중 발생한 문제 및 해결

### 문제 1: Agent Service 초기화 실패 시 전체 서비스 영향
**문제**: Agent Service 초기화가 실패하면 전체 서비스가 중단될 수 있음
**해결**: 지연 초기화 방식 채택, 초기화 실패 시 경고만 출력하고 503 에러 반환

### 문제 2: update_action_item_status에서 meeting_id 조회
**문제**: Action Item ID만으로는 권한 체크를 할 수 없음
**해결**: `get_action_item_meeting_id()` 함수 추가하여 meeting_id 조회 후 권한 체크

### 문제 3: CalendarEvent 형식과 DB 형식 불일치
**문제**: `agent_service.process()` 결과의 `processed_items`는 CalendarEvent 형식
**해결**: DB 저장 시 형식 변환 로직 추가 (`summary` → `content`, `start_time` → `due_date`)

## 개선 가능한 부분

1. **배치 상태 업데이트**: 여러 Action Item을 한 번에 완료 처리하는 기능
2. **필터링**: 완료/미완료 필터링 기능
3. **정렬**: 날짜순, 상태순 정렬 기능
4. **편집 기능**: Action Item 내용 수정 기능
5. **알림**: 마감일 임박 시 알림 기능

## 참고 사항

- Agent Service는 선택적 기능이므로 초기화 실패해도 다른 기능에 영향 없음
- Action Item 추출은 시간이 걸릴 수 있으므로 로딩 상태 표시 중요
- Google Calendar 연동 상태는 `calendar_event_id` 필드로 확인 가능

## Priority 3: 검색 및 필터링 고도화 - 판단 로그 (2025-12-29)

### 작업 개요
노트 목록 페이지에 페이지네이션, 검색, 날짜 범위 필터, 정렬 기능을 추가하여 대량의 데이터를 효율적으로 관리하고 사용자가 원하는 노트를 빠르게 찾을 수 있도록 개선함.

### 주요 판단 사항 및 결정

#### 1. 페이지네이션 방식 선택

**판단**: 무한 스크롤 vs 전통적인 페이지네이션
- **고려 사항**:
  - 모바일 사용자 경험 (무한 스크롤이 더 자연스러움)
  - 웹 사용자 경험 (페이지 번호가 더 명확할 수 있음)
  - 구현 복잡도
  - 서버 부하
- **결정**: 무한 스크롤 방식 채택
- **이유**:
  - 모바일과 웹 모두에서 일관된 경험 제공
  - 사용자가 스크롤만 하면 되므로 직관적
  - IntersectionObserver API로 구현이 간단
  - 서버 사이드 페이지네이션으로 부하 관리 가능
- **구현 방식**:
  - `IntersectionObserver` API 사용
  - 관찰 대상 요소가 뷰포트에 진입하면 다음 페이지 자동 로드
  - `useCallback`으로 함수 재생성 최소화

#### 2. 검색 구현 방식

**판단**: 서버 사이드 vs 클라이언트 사이드 검색
- **고려 사항**:
  - 데이터 양 (많을수록 서버 사이드가 유리)
  - 네트워크 부하
  - 실시간성
- **결정**: 서버 사이드 검색
- **이유**:
  - 대량의 데이터를 클라이언트로 모두 가져올 필요 없음
  - 서버에서 인덱싱된 데이터로 빠른 검색 가능
  - 제목(`title`)과 요약 내용(`minutes_content`) 모두 검색 대상
  - SQL `LIKE` 연산자 사용 (`%search_term%`)

#### 3. 검색 디바운싱

**판단**: 즉시 검색 vs 디바운싱
- **고려 사항**:
  - 사용자 타이핑 속도
  - 서버 부하
  - 사용자 경험
- **결정**: 500ms 디바운싱 적용
- **이유**:
  - 사용자가 타이핑하는 동안 불필요한 API 호출 방지
  - 타이핑을 멈춘 후에만 서버 요청
  - `useEffect`와 `setTimeout`으로 구현
- **구현 방식**:
  - `searchTerm` 상태와 `debouncedSearchTerm` 상태 분리
  - `useEffect`로 500ms 지연 후 `debouncedSearchTerm` 업데이트
  - `debouncedSearchTerm` 변경 시에만 API 호출

#### 4. 날짜 범위 필터 적용 방식

**판단**: 즉시 적용 vs 버튼 클릭 적용
- **고려 사항**:
  - 사용자 의도 (날짜 선택 중 실수로 필터 적용)
  - 사용자 경험 (즉시 피드백 vs 명시적 액션)
- **결정**: "필터 적용" 버튼 방식
- **이유**:
  - 사용자가 날짜를 선택하는 동안 실수로 필터가 적용되는 것을 방지
  - 명시적인 액션으로 사용자 의도 확인
  - "필터 초기화" 버튼도 함께 제공하여 사용성 향상
- **구현 방식**:
  - `startDateInput`/`endDateInput` (UI 입력용)과 `startDate`/`endDate` (실제 필터용) 상태 분리
  - "필터 적용" 버튼 클릭 시 `startDate`/`endDate` 업데이트 및 데이터 재로드

#### 5. 정렬 옵션 UI

**판단**: 드롭다운 vs 토글 버튼
- **고려 사항**:
  - 옵션 수 (드롭다운은 많은 옵션에 유리)
  - 사용 빈도 (자주 사용하는 옵션은 토글이 유리)
  - UI 공간
- **결정**: 토글 버튼 방식 (2개 버튼: 날짜순, 제목순)
- **이유**:
  - 정렬 옵션이 많지 않음 (날짜순, 제목순)
  - 토글 방식으로 클릭 한 번에 정렬 방향 변경 (최신순 ↔ 오래된 순)
  - 직관적이고 공간 효율적
  - 화살표 아이콘으로 정렬 방향 표시
- **구현 방식**:
  - 날짜순 버튼: 클릭 시 `date_desc` ↔ `date_asc` 토글
  - 제목순 버튼: 클릭 시 `title_asc` ↔ `title_desc` 토글
  - 활성화된 버튼은 배경색과 아이콘으로 표시

#### 6. 태그 기반 필터 제외 결정

**판단**: 태그 기반 필터 구현 여부
- **고려 사항**:
  - 태그 기능이 아직 구현되지 않음
  - 우선순위 (다른 기능이 더 중요)
  - 구현 복잡도
- **결정**: 태그 기반 필터 제외 (선택 사항으로 미루기)
- **이유**:
  - 태그 기능 자체가 아직 구현되지 않음
  - 날짜 필터와 정렬 기능으로도 충분한 필터링 가능
  - 향후 태그 기능 구현 시 추가 가능
- **향후 계획**: 태그 기능 구현 후 태그 기반 필터 추가

#### 7. SQL 쿼리 최적화

**판단**: WHERE 절 vs HAVING 절 사용
- **고려 사항**:
  - GROUP BY 사용으로 인한 집계 함수 조건 처리
  - 날짜 필터는 `MAX(meeting_date)`와 비교 필요
- **결정**: WHERE 절과 HAVING 절 분리
- **이유**:
  - 검색어 필터는 WHERE 절에서 처리 (GROUP BY 전)
  - 날짜 범위 필터는 HAVING 절에서 처리 (GROUP BY 후, 집계 함수 사용)
  - 쿼리 성능 최적화
- **구현 방식**:
  - WHERE 절: `title LIKE ? OR minutes_content LIKE ?`
  - HAVING 절: `MAX(meeting_date) >= ? AND MAX(meeting_date) <= ?`

#### 8. 중복 데이터 방지

**판단**: 무한 스크롤 시 중복 데이터 처리
- **고려 사항**:
  - 같은 데이터가 여러 번 표시될 수 있음
  - 페이지 로드 중 데이터 추가/삭제 가능성
- **결정**: `meeting_id` 기준 중복 제거
- **이유**:
  - `Set`을 사용하여 이미 표시된 `meeting_id` 추적
  - 새로 로드된 데이터에서 중복 제거 후 추가
  - 사용자 경험 향상
- **구현 방식**:
  - `Set<meeting_id>`로 표시된 ID 추적
  - `loadMeetings` 함수에서 중복 필터링 후 상태 업데이트

### 구현 중 발생한 문제 및 해결

#### 문제 1: 대시보드 최근 노트 개수
**문제**: `getRecentMeetings`에서 `perPage: 5`로 설정했지만 대시보드에 14개 노트가 표시됨
**해결**: `Dashboard.tsx`에서 `.slice(0, 5)`로 명시적으로 제한

#### 문제 2: 무한 스크롤 중복 데이터
**문제**: 스크롤을 내리면 이전 노트가 반복해서 나타남
**해결**: `loadMeetings` 함수에서 `meeting_id` 기준 중복 제거 로직 추가

#### 문제 3: 날짜 필터 즉시 적용 문제
**문제**: 날짜를 선택하는 순간 필터가 적용되어 사용자가 날짜를 완전히 선택하기 어려움
**해결**: 입력 상태와 필터 상태 분리, "필터 적용" 버튼 추가

#### 문제 4: 정렬 옵션 드롭다운 복잡도
**문제**: 드롭다운에 많은 옵션이 있어 선택이 복잡함
**해결**: 토글 버튼 방식으로 변경, 클릭 한 번에 정렬 방향 변경

### 개선 가능한 부분

1. **태그 기반 필터**: 태그 기능 구현 후 추가
2. **검색 결과 하이라이팅**: 검색어 강조 표시
3. **필터 저장**: 사용자가 설정한 필터를 로컬 스토리지에 저장
4. **고급 필터**: 참석자별, 시간대별 필터 추가

### 참고 사항

- 서버 사이드 검색으로 대량 데이터 처리 가능

## Priority 4: 오디오 플레이어 고도화 - 판단 로그 (2025-12-29)

### 작업 개요
노트 상세 페이지의 오디오 플레이어에 재생 속도 조절, 구간 반복 재생, 파형 시각화 기능을 추가하고, 비디오 파일 재생 기능을 구현함. 이를 통해 사용자가 회의록을 더 효율적으로 검토하고 필요한 구간을 반복하여 들을 수 있도록 개선함.

### 주요 판단 사항 및 결정

#### 1. 재생 속도 범위 결정

**판단**: 재생 속도 옵션 범위 및 단계
- **고려 사항**:
  - 일반적인 오디오 플레이어의 재생 속도 범위
  - 사용자 요구사항 (빠르게 듣기, 천천히 듣기)
  - HTML5 Media API 제한사항
- **결정**: 0.5x, 0.75x, 1.0x, 1.25x, 1.5x, 1.75x, 2.0x (7단계)
- **이유**:
  - 0.5x: 매우 빠른 발화를 천천히 들을 때
  - 0.75x: 약간 빠른 발화를 들을 때
  - 1.0x: 정상 속도
  - 1.25x ~ 2.0x: 긴 회의록을 빠르게 검토할 때
  - HTML5 Media API가 0.25x ~ 4.0x 범위를 지원하지만, 실용적인 범위로 제한
- **구현 방식**:
  - 드롭다운 UI로 재생 속도 선택
  - `media.playbackRate` 속성에 직접 적용
  - 오디오와 비디오 모두 지원

#### 2. 구간 반복 재생 방식

**판단**: A-B 마커 방식 vs 다른 방식
- **고려 사항**:
  - 사용자 친화성
  - 구현 복잡도
  - 일반적인 오디오 플레이어 패턴
- **결정**: A-B 마커 방식 (시작점/끝점 설정)
- **이유**:
  - 직관적이고 일반적인 패턴
  - 사용자가 원하는 구간을 정확히 선택 가능
  - 재생바에 시각적 하이라이트로 반복 구간 표시
- **구현 방식**:
  - 반복 시작점 설정 버튼: 현재 재생 시간을 `loopStart`로 설정
  - 반복 끝점 설정 버튼: 현재 재생 시간을 `loopEnd`로 설정
  - 반복 재생 토글 버튼: `isLooping` 상태 토글
  - `handleTimeUpdate`에서 반복 구간 도달 시 `loopStart`로 이동
  - 재생바에 반복 구간 하이라이트 표시

#### 3. 파형 시각화 라이브러리 선택

**판단**: WaveSurfer.js vs 다른 라이브러리 vs 직접 구현
- **고려 사항**:
  - 기능 완성도
  - 커뮤니티 지원
  - 번들 크기
  - 오디오 재생과의 동기화
- **결정**: WaveSurfer.js 사용
- **이유**:
  - 오디오 파형 시각화에 특화된 라이브러리
  - 오디오 재생과 파형 시각화 동기화 기능 제공
  - 파형 클릭 시 해당 시간으로 이동 기능 (`seek` 이벤트)
  - WebAudio 백엔드로 고품질 파형 생성
  - 활발한 커뮤니티 지원
- **구현 방식**:
  - `WaveSurfer.create()`로 인스턴스 생성
  - `wavesurfer.load(audioUrl)`로 오디오 로드
  - 오디오 재생/일시정지와 파형 동기화
  - `timeupdate` 이벤트로 파형 커서 위치 업데이트
  - `seek` 이벤트로 파형 클릭 시 오디오 시간 이동

#### 4. 파형 시각화 표시 조건

**판단**: 항상 표시 vs 토글 버튼
- **고려 사항**:
  - UI 공간
  - 사용자 선택권
  - 성능 (파형 생성은 리소스 사용)
- **결정**: 토글 버튼 방식 (오디오만)
- **이유**:
  - 파형 시각화는 선택적 기능
  - UI 공간 절약
  - 사용자가 필요할 때만 활성화
  - 비디오는 시각적 재생이 있으므로 파형 불필요
- **구현 방식**:
  - 파형 시각화 토글 버튼 추가 (Network 아이콘)
  - `showWaveform` 상태로 표시 여부 제어
  - 오디오인 경우에만 버튼 표시

#### 5. 오디오/비디오 통합 방식

**판단**: 별도 처리 vs 통합 처리
- **고려 사항**:
  - 코드 중복
  - 유지보수성
  - HTML5 Media API 공통 인터페이스
- **결정**: 통합 처리 (`media` 변수로 동적 선택)
- **이유**:
  - `HTMLAudioElement`와 `HTMLVideoElement`는 모두 `HTMLMediaElement` 상속
  - `currentTime`, `duration`, `playbackRate`, `play()`, `pause()` 등 공통 API
  - 코드 중복 최소화
  - 유지보수 용이
- **구현 방식**:
  - `meeting?.is_video`로 오디오/비디오 요소 선택
  - 모든 이벤트 리스너와 컨트롤이 오디오/비디오 모두에서 작동
  - 비디오는 시각적 재생, 오디오는 파형 시각화 제공

#### 6. 영상 재생 기능 추가

**판단**: 영상 재생 기능 구현 여부
- **고려 사항**:
  - 사용자 요구사항 (업로드/녹화한 영상 재생)
  - 구현 복잡도
  - 오디오 플레이어와의 통합
- **결정**: 영상 재생 기능 추가
- **이유**:
  - 사용자가 업로드하거나 녹화한 영상 파일을 직접 재생할 수 있어야 함
  - 오디오 플레이어와 동일한 컨트롤 사용으로 일관된 UX
  - HTML5 `<video>` 태그로 간단히 구현 가능
- **구현 방식**:
  - 백엔드: 파일 확장자로 비디오 여부 판단 (`.mp4`, `.webm`, `.mov`, `.avi`, `.mkv`)
  - API 응답에 `is_video` 필드 추가
  - 프론트엔드: 비디오인 경우 `<video>` 태그 사용
  - 비디오 플레이어에 최대 높이 제한 (400px)

#### 7. 비디오 여부 판단 방식

**판단**: 파일 확장자 vs MIME 타입 vs 메타데이터
- **고려 사항**:
  - 정확도
  - 구현 복잡도
  - 성능
- **결정**: 파일 확장자로 판단
- **이유**:
  - 간단하고 빠름
  - 대부분의 경우 정확함
  - 데이터베이스에 저장된 파일명으로 판단 가능
  - MIME 타입은 업로드 시점에만 확인 가능하므로 저장된 파일에는 부적합
- **구현 방식**:
  - 비디오 확장자 리스트: `['.mp4', '.webm', '.mov', '.avi', '.mkv']`
  - `audio_file`의 확장자로 판단
  - API 응답에 `is_video` 필드 포함

#### 8. 파형 시각화 동기화

**판단**: 오디오 재생과 파형 시각화 동기화 방식
- **고려 사항**:
  - 정확도
  - 성능
  - 구현 복잡도
- **결정**: 양방향 동기화
- **이유**:
  - 오디오 재생 시 파형 커서도 이동
  - 파형 클릭 시 오디오 시간도 이동
  - 사용자 경험 향상
- **구현 방식**:
  - 오디오 `timeupdate` 이벤트: 파형 `seekTo()` 호출
  - 파형 `seek` 이벤트: 오디오 `currentTime` 설정
  - 0.1초 이상 차이날 때만 동기화 (무한 루프 방지)

### 구현 중 발생한 문제 및 해결

#### 문제 1: 파형 시각화 useEffect 중복
**문제**: 파형 시각화 useEffect가 중복으로 생성됨
**해결**: 중복된 useEffect 제거, 하나만 유지

#### 문제 2: 파형 클릭 시 세그먼트 선택
**문제**: 파형 클릭 시 오디오 시간은 이동하지만 세그먼트가 선택되지 않음
**해결**: `seek` 이벤트 핸들러에서 세그먼트 찾기 로직 추가

#### 문제 3: 오디오/비디오 통합 시 이벤트 리스너
**문제**: `audio` 변수를 `media`로 변경했지만 일부 함수에서 여전히 `audio` 사용
**해결**: 모든 함수에서 `media` 변수 사용하도록 통일

### 개선 가능한 부분

1. **파형 시각화 고급 기능**: 줌, 스펙트로그램 표시
2. **재생 속도 프리셋**: 사용자가 자주 사용하는 속도 저장

## Priority 5: 대용량 처리 비동기화 - 작업 계획 수립 (2025-12-29)

### 작업 개요
현재 시스템의 동기 처리 방식에서 발생하는 문제점을 해결하기 위해 비동기 처리 시스템 도입을 계획함. 단계적 접근을 통해 복잡도를 관리하면서 확장성과 안정성을 확보하는 것을 목표로 함.

### 주요 판단 사항 및 결정

#### 1. 비동기화 필요성 판단

**판단**: 현재 시스템의 동기 처리 방식이 문제가 되는가?
- **현재 상황**:
  - 파일 업로드 → 비디오 변환 → STT → 요약 → 마인드맵 (순차 실행)
  - 총 소요 시간: 2-7분
  - SSE 스트리밍으로 진행 상황 전달
- **문제점**:
  - 블로킹 작업으로 인한 긴 처리 시간
  - 동시 업로드 시 서버 부하 및 타임아웃 위험
  - 중간 실패 시 전체 재시작 필요
- **결정**: 단계적 비동기화 도입
- **이유**: 
  - 현재는 SSE로도 사용자 경험이 나쁘지 않음
  - 하지만 동시 업로드가 많아지면 문제 발생 가능
  - 미리 대비하여 확장성 확보

#### 2. 비동기화 방식 선택

**판단**: Celery vs Redis Queue 직접 사용
- **고려 사항**:
  - Celery: 기능이 많지만 복잡도 높음
  - Redis Queue 직접 사용: 단순하지만 기능 제한적
- **결정**: 단계적 접근
  - **Phase 1**: Redis Queue 직접 사용 (경량 비동기화)
  - **Phase 2**: 필요 시 Celery 도입
- **이유**:
  - 복잡도를 단계적으로 관리
  - Phase 1으로 충분할 수 있음
  - 필요 시 Phase 2로 확장 가능

#### 3. 상태 관리 방식

**판단**: 작업 상태를 어디에 저장할지
- **고려 사항**:
  - Redis: 빠르지만 영구 보관 아님
  - 데이터베이스: 영구 보관 가능하지만 느림
  - Celery 자동 관리: Celery 사용 시
- **결정**: Phase 1에서는 Redis 사용, 필요 시 DB 추가
- **이유**:
  - 빠른 접근 속도
  - 작업 완료 후 영구 보관이 필요하면 DB에 저장
  - 단순한 구현

#### 4. 프론트엔드 상태 확인 방식

**판단**: 폴링 vs WebSocket
- **고려 사항**:
  - 폴링: 구현 간단, 주기적 요청으로 서버 부하
  - WebSocket: 실시간 알림, 구현 복잡
- **결정**: Phase 1에서는 폴링, Phase 2에서 WebSocket 고려
- **이유**:
  - 빠른 구현 가능
  - 서버 부하는 작업 수가 많지 않으면 문제 없음
  - 필요 시 WebSocket으로 전환 가능

#### 5. 인프라 요구사항

**판단**: Redis 서버 운영 필요성
- **고려 사항**:
  - Redis 서버 설치 및 운영 필요
  - 메모리 관리 필요
  - 백업 및 복구 계획 필요
- **결정**: Redis 서버 운영 필수
- **이유**:
  - 큐 저장소로 필수
  - 상태 저장소로도 사용
  - Docker로 간단히 운영 가능

### 구현 계획

#### Phase 1: 경량 비동기화 (우선 권장)
1. **Redis 설치 및 설정** (1-2시간)
   - Docker 또는 직접 설치
   - Redis 연결 설정
2. **간단한 큐 시스템 구현** (2-3시간)
   - Redis Queue 사용
   - 작업 등록 함수 구현
3. **Worker 프로세스 구현** (3-4시간)
   - 별도 Python 스크립트로 Worker 실행
   - 큐에서 작업 가져와서 처리
4. **API 엔드포인트 수정** (2-3시간)
   - `/upload`: 즉시 응답 (202 Accepted)
   - `/api/upload/status/<task_id>`: 상태 조회 API
5. **프론트엔드 수정** (2-3시간)
   - 폴링 방식으로 상태 확인
   - 진행 상황 표시
- **총 예상 작업 시간**: 8-12시간

#### Phase 2: Celery 도입 (향후)
1. **Celery 설정** (2-3시간)
2. **작업 분리** (4-6시간)
3. **작업 체인 구성** (3-4시간)
4. **모니터링 도구** (2-3시간)
