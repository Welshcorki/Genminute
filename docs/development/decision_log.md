# GenMinute 결정 기록 (Decision Log)

`dev_log.md`가 "무엇을 했는가"의 전체 기록이라면, 이 파일은 그중 **선택지가 있었던 결정**만 뽑은 짧은 카드 모음이다. 포트폴리오와 면접 답변의 재료로 쓴다.

- 카드는 `/devlog` 커맨드가 추가한다. 단, **`내 이유` 칸은 본인이 직접 쓴다.**
- `내 이유`가 `(작성 전)`인 카드는 포트폴리오에 쓰지 않는다. 본인 말로 설명할 수 없는 결정이기 때문이다.
- 최신 카드가 아래에 온다. 기존 카드는 고치지 않고, 결정이 바뀌면 새 카드를 만들어 `이전 결정: D-NNN`으로 연결한다.

## 카드 형식

```markdown
---

## D-NNN · YYYY-MM-DD · <결정을 한 줄로>

- **상태**: 적용 | 미적용 | 결정 대기 | 번복(→ D-NNN)
- **상황**: <어떤 문제나 필요가 있었는가. 2줄 이내>
- **선택지**
  - A. <안> — <장점 / 단점>
  - B. <안> — <장점 / 단점>
- **결정**: <고른 안과 그 직접적인 근거>
- **근거**: 커밋 `abc1234`, `경로/파일.py`, dev_log "<항목 제목>"
- **결과**: <실측 수치 또는 확인한 동작. 없으면 `미측정` / `미검증`>
- **내 이유**
  > (작성 전)
- **예상 질문**: <면접관이 이 결정에 대해 물을 만한 질문 1개>
```

### 작성 규칙

1. 수치는 직접 실행해 얻은 것만 쓴다. 없으면 `미측정` 또는 `미검증`.
2. "개선", "최적화", "향상"은 전후 수치와 함께일 때만 쓴다.
3. 짐작한 내용에는 `(추정)`을 붙인다.
4. 근거 칸이 비는 카드는 만들지 않는다.

### `내 이유`를 쓸 때

2~4문장이면 된다. 아래 중 답할 수 있는 것을 본인 말로 쓴다.

- 왜 다른 안이 아니라 이 안인가?
- 이 결정으로 포기한 것은 무엇인가?
- 지금 다시 한다면 똑같이 할 것인가?

에이전트가 제안한 결정을 그대로 받아들였다면 그렇게 쓴다 (예: "에이전트 제안을 수용. 실측 표를 보고 영상이 사라지는 문제를 확인한 뒤 동의함"). 그것도 사실이고, 면접에서 방어할 수 있다.

## D-001 · 2026-11-16 · 브라우저 녹음 WebM 변환 함수를 다시 연결하지 않음

> 예시 카드 — dev_log "연결이 끊긴 기능 검증: 스크립트 입력 복구, WebM 변환은 보류" 항목에서 옮김. 내용이 맞는지 확인하고 `내 이유`를 채우면 실제 카드가 된다.

- **상태**: 결정 대기 (재포장 방식은 미적용)
- **상황**: `upload_service.convert_webm_to_compatible_format`가 호출부 없이 남아 있었다. 삭제할 죽은 코드인지, 연결이 끊긴 기능인지 판단이 필요했다. 한편 브라우저가 녹음한 WebM에는 길이 정보가 없어(`duration=N/A`) 탐색 바와 구간 반복이 제대로 동작하기 어렵다.
- **선택지**
  - A. 기존 함수를 업로드 흐름에 다시 연결 — 코드가 이미 있음 / 파일명에 `video_` 접두어가 있어야 영상으로 취급하는데 현재 React 녹음 화면은 접두어를 붙이지 않아 화면 녹화의 영상이 사라짐
  - B. 재인코딩 없이 재포장(`ffmpeg -c copy`)으로 길이 정보만 채움 — 영상 보존, 빠름 / 새로 구현해야 함
  - C. 함수 삭제 — 정리는 되지만 길이 정보 문제는 그대로 남음
- **결정**: A는 하지 않는다. B를 권장안으로 두고 적용은 보류한다.
- **근거**: 커밋 `b88c8ff`, `services/upload_service.py`, 과거 비활성화 커밋 `66eee00`, dev_log 2026-11-16 실측 표
- **결과**: 실측(ffmpeg 8.0.1) — 화면 녹화 47초(13.8MB, 접두어 없음)를 기존 함수로 변환하면 M4A 0.7MB가 되어 영상이 사라짐(1.2초). 재포장은 13.8MB 유지, 길이 정보 생김(0.1초). 재포장을 실제 업로드 흐름에 넣은 뒤의 동작은 `미검증`.
- **내 이유**
  > (작성 전)
- **예상 질문**: 호출부가 없는 함수를 바로 삭제하지 않고 실제로 돌려 본 이유는 무엇인가요?

## D-002 · 2026-11-19 · 배포 저장소를 Firestore + Firebase Storage(`us-central1`)로 정함

- **상태**: 미적용 (계획 확정, 구현은 2단계 직후)
- **상황**: Cloud Run은 디스크가 유지되지 않아 SQLite·ChromaDB·`uploads/`를 그대로 둘 수 없다. 요청 크기도 32MiB로 제한되어 큰 녹음 파일을 서버로 직접 받기 어렵다.
- **선택지**
  - A. Firestore(+벡터 검색) + Cloud Storage for Firebase — 로그인·키·결제가 이미 쓰는 프로젝트 하나로 모임, 브라우저 직접 업로드로 32MiB 제한 회피 / repo 구현을 새로 써야 하고 NoSQL에 맞게 데이터를 다시 설계해야 함
  - B. Supabase(Postgres + pgvector) — 구현이 이미 있음, 테이블 구조 그대로 / 동작 미검증, 업체가 하나 더 늘어남
- **결정**: A. 리전은 GPU를 쓸 수 있는 `us-central1`(사용자 결정). Firestore는 위치를 나중에 바꿀 수 없어 Cloud Run과 같은 리전으로 만든다.
- **근거**: `docs/development/post_refactoring_plan_handoff.md` "추가 단계 A", 커밋 `f1d6a27`, `database/repositories/sqlite/connection.py`(손볼 기존 구조 7건)
- **결과**: `미검증`. 리전별 단가는 가격 페이지 조회 실패로 미확인. Firestore 벡터 검색의 회의 ID 필터 제한도 미확인.
- **내 이유**
  > 참여했던 교육 과정에서 다루기도 했고, Firestore를 사용하면 Supabase의 DB를 사용하지 않으면서 한 프로젝트에서 관리하기 용이하다고 판단했음. 로컬 STT를 서버로 돌릴 경우, GCP에서 확인한 등급에 따라 GPU 사용이 가능하면서 비용이 상대적으로 저렴한 us-central1 리전을 선택. 대신 데이터 구조를 NoSQL에 맞게 다시 짜야 하는 부담을 감수함.
- **예상 질문**: 관계형 구조(공유·권한)를 가진 앱을 NoSQL로 옮길 때 무엇을 가장 먼저 다시 설계해야 하나요?

## D-005 · 2026-11-20 · 배포를 Firebase Hosting + Cloud Run으로 하고, 이 PC의 Docker Desktop은 쓰지 않음

- **상태**: 미적용 (계획 확정, 8단계에서 적용)
- **상황**: 배포할 곳을 정해야 했다. Docker는 앱을 포장하는 도구라 어느 안이든 쓰지만, 그 이미지를 어디서 돌릴지가 비용과 작업량을 가른다.
- **선택지**
  - A. Firebase Hosting(화면) + Cloud Run(서버) — 고정비 0, HTTPS·무료 주소 자동 / Firestore 이전, 응답 후 처리 재설계, 브라우저 직접 업로드가 필요
  - B. GCP VM + Docker — SQLite·ChromaDB·`uploads/`를 그대로 둘 수 있음 / 월 고정비(추정 2~3만원), 서버 관리 직접
  - C. 이 PC + Docker Desktop + Tailscale/Cloudflare Tunnel — 0원 / PC를 계속 켜 둬야 하고, Hosting과 섞으면 주소가 둘로 나뉨, Intel GPU라 컨테이너 안 GPU 가속 어려움
- **결정**: A. 사용자 발언 "Docker Desktop은 개인용 앱을 돌릴때만 사용하고(GenMinute 아님), 지금 조합(Firestore + Hosting + Cloud Run, 모두 us-central1)으로 그대로 진행할게."
- **근거**: `docs/development/post_refactoring_plan_handoff.md` 8단계·2절 1번·3절, decision_log `D-002`
- **결과**: `미검증`. 월 예상 비용 약 $1.5~3(대부분 Gemini 호출)은 추정이며 `미측정`.
- **내 이유**
  > 개인 규모 서비스라 사용량이 적을 때 비용을 최대한 줄일 수 있는 방법을 고려. VM은 작업량이 적지만 쓰지 않아도 매달 고정비가 나가고, PC + Docker Desktop은 무료지만 PC를 계속 켜 둬야 해서 다른 사람이 쓰는 서비스에는 맞지 않는다고 판단. 대신 Firestore 이전과 업로드 방식 재설계라는 작업량을 감수했고, 이 작업 때 기존 DB 구조 문제도 함께 정리할 수 있다는 점도 고려했다.
- **예상 질문**: 고정비가 없는 대신 작업량이 늘어나는 Cloud Run을, 작업량이 적은 VM 대신 고른 이유는 무엇인가요?

## D-006 · 2026-11-20 · 배포 서버의 Firebase 관리자 인증을 키 파일 대신 ADC + 전용 서비스 계정으로 함

- **내 이유**
  > 처음에는 키를 Secret Manager에 넣고 노출만 조심하면 된다고 생각했다. 그런데 Secret Manager에서 키를 꺼내 오는 데에도 결국 서비스 계정 인증(ADC)이 필요하고, 서버에 연결된 키는 만료 없는 관리자 키라 서버가 뚫리면 그대로 넘어간다는 설명을 듣고 생각을 바꿈. 코드 몇 줄만 고치면 서버에 장기 키를 두지 않고 권한도 필요한 만큼만 줄 수 있어 ADC로 정했다. 비용 차이가 없다는 것도 공식 문서로 확인했다.
- **예상 질문**: 비밀값 관리 서비스에 키를 넣으면 안전하지 않나요? 왜 그것만으로는 부족하다고 판단했나요?
